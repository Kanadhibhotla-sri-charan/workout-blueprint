# Programming Knowledge

Human-readable explanation of the hypertrophy-programming layer added in Phase 4. The **authoritative, machine-readable** data lives in [`data/programming/`](../../../data/programming/) — this page explains what's there and why; it does not duplicate the actual guidance.

## Why this exists

Phase 3's Decision Maker answers *which exercise*. Phase 4 adds *how to train it for growth* — sets, reps, RIR, frequency, and progression — without turning the application into an AI coach. Every number the engine produces traces back to one of the files below through an explicit, deterministic rule; nothing is inferred or generated per-request. See [`docs/architecture/PHASE-4-PHYSIQUE-TARGET-AND-HYPERTROPHY.md`](../../architecture/PHASE-4-PHYSIQUE-TARGET-AND-HYPERTROPHY.md) for the full spec and [ADR 0003](../../adr/0003-physique-targets-field.md) for the taxonomy's schema rationale.

## The seven files

- **`functional-goals.yaml`** — the authoritative definition of the Function branch (revised Phase 4 spec §12/§39): joint-durability and movement-quality goals (rotator cuff, scapular stability, hip flexors, hip stability, core anti-extension/anti-rotation/anti-lateral-flexion) that feed the same downstream engine as physique targets, through their own `functional_goals` field on exercise records, kept structurally and conceptually separate from the aesthetic outcome layer — never mixed into the Appearance selector.
- **`aesthetic-outcomes.yaml`** — the authoritative definition of the Aesthetic Outcome layer added by the revised Phase 4 spec: canonical, mirror-recognizable visual characteristics (e.g. "Chest looks flat from the side"), organized by region and viewpoint. Each outcome references `physique-targets.yaml` ids via an explicit `primary_targets`/`supporting_targets` split (Phase 4 Corrections) rather than a flat list — the primary target drives exercise selection, supporting targets broaden the candidate pool and are surfaced in the UI, and neither is ever silently discarded. An outcome may also carry `preferred_characteristics` (Phase 4C §2-4) — a short list from the `aesthetic_characteristics` vocabulary (see below) that refines *which* target-matched exercise wins, for outcomes where several correctly-target-matched exercises aren't equally suited to the exact visual problem. A small number of outcomes additionally carry `exercise_roles` (Phase 4C Final Correction §4-6) — an explicit, outcome-contextual mapping of `primary`/`direct`/`secondary`/`supporting` to specific exercise ids, for the rare cases where the knowledge base already establishes a clear "which of these same-target exercises is the better tool for this exact visual problem" distinction that neither `physique_targets` nor `preferred_characteristics` fully captures (e.g. Standing Calf Raise vs. Leg Press Calf Raise for calf width/shape). Roles are never a global exercise property — the same exercise can carry a different role, or none, on a different outcome — and are only added where a real ranking bug demonstrated the need, never as an exhaustive exercise × outcome matrix. See `docs/architecture/PHASE-4-REVISED-AESTHETIC-OUTCOME.md`, `docs/architecture/PHASE-4-CORRECTIONS.md`, `docs/architecture/PHASE-4C-AESTHETIC-SUITABILITY.md`, `docs/architecture/PHASE-4C-FINAL-AESTHETIC-EXERCISE-ROLE.md`, and `docs/dev/reports/PHASE-4-AESTHETIC-TAXONOMY-PROPOSAL.md` for the audit that grounds every outcome in real exercise data rather than invented categories.
- **`physique-targets.yaml`** — the authoritative definition of what a physique target *means* (e.g. "Upper Pec": the clavicular portion of the pectoralis major, the visible outcome it maps to). Exercise records reference these ids via their own `physique_targets` field; this file does not list exercises, to avoid a second taxonomy that could drift out of sync. See ADR 0003.
- **`global-principles.yaml`** — RIR, weekly volume, frequency, and progression guidance that applies broadly, not per-exercise or per-target.
- **`programming-profiles.yaml`** — the Programming Profile catalog (Phase 4B §10-11): a reusable, deterministic classification layer (8 profiles) between "what exercise is this" and "what programming guidance applies," derived from existing exercise metadata (`exercise_type`, `coverage_categories`, `stability_demand`) rather than a hand-written prescription per exercise. Each profile carries its own rep range plus a distinct `guidance_note` — this is what `rep-ranges.yaml`'s old `defaults:` classification logic moved into, so rep range and programming framing come from one shared lookup rather than being duplicated.
- **`rep-ranges.yaml`** — exercise-specific rep-range *overrides* only, for the rare case a specific exercise needs to deviate from its Programming Profile's default. The override list starts empty and stays empty unless a genuine, defensible distinction requires one — it is not meant to be populated per-exercise.
- **`intensity-techniques.yaml`** — a small catalog of optional techniques (drop sets, rest-pause, myo-reps for the Phase 4 v1 slice), each with what it is, when it may help, when not to use it, and its fatigue/time cost. The engine suggests at most one, only when a clear, deterministic condition is met — never presented as a required or automatically-superior addition.

## Evidence basis

Per the architect's approval of the "practical consensus ranges, lightly sourced" approach: this guidance reflects broadly-converged, widely-taught hypertrophy-coaching consensus, not per-line research citations the way `data/exercises/*.yaml`'s `evidence_notes` field works. Every range is a **starting point to adjust**, not an exact physiological law — see `global-principles.yaml`'s `wording_rules` for the specific language the application is required to use (and avoid) when presenting these numbers.

## What's deliberately not here

Per the Phase 4 spec's explicit scope boundary: no periodization model beyond simple double progression, no recovery/fatigue prediction, no training-experience (beginner/intermediate/advanced) personalization, no fiber-type-based rep prescriptions. If real-world use later demonstrates a need for any of these, they're a future decision, not an oversight here.
