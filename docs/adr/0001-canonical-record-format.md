# ADR 0001: YAML as the canonical exercise-record format

**Status:** Accepted  
**Date:** 2026-08-14  
**Resolves:** `PDD.md` §12, "YAML, JSON, or TypeScript as the canonical exercise-record format."

## Context

`FOUNDATION.md` defines a ~30-field canonical exercise-record schema, but every record produced so far (124, across 11 muscle modules) is hand-written prose in an abbreviated 9-field subset of that schema, living in `docs/knowledge-manual/`. Nothing machine-readable exists yet. The PDD's own roadmap (§10, V1) requires converting this content into normalized records before any browse, search, filter, or comparison feature can be built, and the PDD's governance section (§9) requires an ADR for material schema decisions — this is the most material one in the project so far, since every future feature reads through whatever this decision produces.

Three formats were on the table:

- **YAML** — human-readable, diffable in plain git history, tolerant of long multi-line prose fields (the schema has several: `why_this_exists`, `mirror_effect`, free-text lists), no build step to read or write it.
- **JSON** — same structural capability as YAML, but no comments, worse multi-line string ergonomics, and less approachable for a non-engineer reviewing or editing a record by hand.
- **TypeScript** — would give compile-time schema validation for free, but couples the canonical data to a specific runtime and build toolchain before the application layer (`app/`) exists at all, and is a real barrier to a subject-matter contributor who isn't a developer.

## Decision

Canonical records are written in **YAML**. One file per muscle module, living in a new top-level `data/exercises/` directory, mirroring the existing `docs/knowledge-manual/<region>/` structure:

```
data/exercises/chest.yaml
data/exercises/back.yaml
data/exercises/shoulders.yaml
... (one per module)
```

Each file holds a YAML list of record objects, each following `FOUNDATION.md`'s schema. Fields with no source material yet (`technique_cues`, `common_mistakes`, `programming_notes`, `evidence_notes`, `alternatives` as distinct from `overlaps_with`) are left as empty lists rather than fabricated — populating them is separate, later work, not a byproduct of this format conversion.

The prose in `docs/knowledge-manual/` is not being retired. It stays as the human-readable working draft and discussion surface; `data/exercises/` becomes the structured source of truth `PDD.md` §9 describes, generated by converting the prose, not by rewriting from scratch.

### ID scheme

`id` is a stable, human-readable slug (matching `FOUNDATION.md`'s `id: stable-slug`). Where a genuinely distinct technique variant already has its own record — not a lookup convenience, an actual different exercise per the separate-variation rule — the slug carries that distinction, e.g. `bulgarian-split-squat-hip-dominant` / `bulgarian-split-squat-knee-dominant`, `dip-chest-biased` / `dip-triceps-biased`.

### Open sub-decision: genuinely identical cross-module records

Several records were deliberately duplicated across two prose files for reader convenience — most notably the Romanian deadlift (hips and hamstrings), which this session's audit confirmed has no execution fork distinguishing the two copies; they are the same exercise, filed under two modules because it's a primary hip-extension movement and a primary hamstring movement at once. Bulgarian split squat and the 45° back extension, by contrast, *do* have real execution forks and are correctly two distinct records.

In structured data, physically duplicating an identical record is a maintenance liability — the two copies can drift apart, which is exactly the failure mode this session's audits kept finding in the prose. This ADR proposes, but does not yet finalize, that genuinely identical cross-module exercises become a **single record with a multi-value `body_regions` field**, tagged into both modules' data files (or referenced from both, format TBD) rather than physically duplicated. This needs confirmation before the hips, hamstrings, back, and quads files are converted, since it changes how those specific records are represented — the other modules aren't affected and can be converted under the plain one-record-per-file-list model without waiting on this.

## Consequences

- Conversion work is now unblocked for modules that don't hit the dedup question.
- The dedup question must be resolved before converting hips, hamstrings, back, and quads.
- Populating the schema's currently-empty fields (evidence notes, technique cues, etc.) is separate follow-on work — this ADR only settles the container format, not the content-completeness gate PDD.md §12 also leaves open (review threshold, minimum reviewed starter set).
